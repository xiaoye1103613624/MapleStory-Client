⇒ **内容原点 = ref (53, 81) = 边框 + 6**，与 `backdrop.draw(pos + Point(-6, -6), FRAME_WIDTH + 12, height + 32)` 一致；
框体总高 = 360-75+1 = **286** ⇒ `height = 254`。

分隔线右界实测停在 **lx 263**（lx264 已是底色）⇒ `FRAME_WIDTH = 264` 逐像素坐实。
右边框在 ref x322，超出截图（宽 319）⇒ 框宽 276 只能间接由「左 + 264 + 右各 6」推得，**未直证**。

`height` 复核：`height = 540`（上游原值）− 16（无潜能）− 18（非武器）− 18×14（15 条 EquipStat 里 14 条为空，本件只有 DEF）= **254** ⇒ 框高 286 ✓ 与原生一致，无需改动。

## 4. 唯一实质改动：职业名回退为原生「同原点叠绘」

原生 y159..169 x10..45 是一块 36×11 的**白色糊块**，不是可读的职业名行。

把 `UIWindow.img/ToolTip/Equip/Can` 下 6 张职业名（beginner 40×13 / warrior 38 / magician 38 /
bowman 37 / thief 24 / pirate 29，墨点 x 并集 0..35、y 并集 1..11）按**同一原点**叠绘合成，
与原生该 36×11 区域对拍：

| 画法 | 全区域 SAD | 仅原生墨点 SAD |
| --- | --- | --- |
| **6 张同原点叠绘** | **0.12** | **0.00** |
| 单张 beginner | 134.48 | 163.71 |
| 单张 warrior | 142.66 | 173.68 |
| 单张 magician | 94.75 | 115.31 |
| 单张 bowman | 114.03 | 138.80 |
| 单张 thief | 147.91 | 180.08 |
| 单张 pirate | 128.05 | 155.88 |

⇒ 原生确实是「6 张叠在同一坐标」，且我们的素材/原点/alpha 与之逐像素等价（SAD=0.00）。
上游 `git show HEAD:IO/Components/EquipTooltip.cpp` 第 702-703 行也正是这个写法：

```cpp
for (auto& jbit : okjobs)
    jobs[canequip[MapleStat::Id::JOB]].at(jbit).draw(job_position);
```

W5 曾按 B8.4 把它改成「逐个横排」（可读、宽 218px），**属于偏离原生**——
当时判为缺陷的真因是线上 `jobs[]` 取自不存在的 `UIToolTip.img/Item/Equip/Job/*` ⇒ 空纹理，
跟叠绘无关；路径改对（`UIWindow.img/ToolTip/Equip/Can|Cannot/*`）后叠绘即还原原生。

**改动**：`IO/Components/EquipTooltip.cpp` 主窗与对比预览窗两处循环回退为同原点叠绘。
副作用（预期内、与原生一致）：reqjob=0 的装备在职业名处显示一团白块。
若更看重可读性，把循环改回横排即可（一行 `job_x += job.width() + 2`），列为需用户拍板项。
