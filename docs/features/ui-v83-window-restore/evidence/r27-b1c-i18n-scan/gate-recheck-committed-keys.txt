## 3. 结论
  · 本批可复核不变量 = 提交树键数增量：188 (5a) -> 286 (5b) -> 301 (5c)，净增 +98 / +15，与键表行数一致。
  · 归档里 288 / 303 是**当时的工具 stdout（工作树读数）**，各含并行会话未提交的 2 条 sysopt.combo.* —— 数字不假，但口径错：不能当「本批建了多少键」读。
  · 「代码引用键 N 个」同理是工作树源码读数，会随别人的未提交件漂移（5b 归档 215 / 5c 归档 232 / 现在重跑 230），只能作为当时快照，不可当不变量。
  · 修法：尺子自己打两行（工作树 + HEAD 提交树），归档一律引提交树那一行。

今天两行各比归档**少 2**。尺子没变（5c 那版就是 `0053765` 提交的），源码里我的部分也没变（5c 之后只提了文档），

## 5. 复核当场撞上的第二次口径事故：`HEAD` 自己会动

本档案 §1 的表**逐 rev 写死**，所以上面那些数字永远成立。但 §2 用的是 `HEAD`，而写成 §2 之后几分钟里
并行会话提交了 `aa0d4e2`（R28-B4 系统设置），把当时那 6 条「未提交的 `sysopt.combo.*`」**提进了提交树**：

```
$ git show HEAD:locale/zh-CN.ini | grep -cE '^[a-z][^=]*='      # HEAD=aa0d4e2 之后
307
$ git show e0fbb7b:locale/zh-CN.ini | grep -cE '^[a-z][^=]*='   # 同一句话，钉 rev
301
```

⇒ 结论（已固化进尺子）：**任何「提交树」读数必须带 rev**，写 `HEAD` 等于写一个会过期的数。
`check_locale_keys.py` 现在打的是 `HEAD(aa0d4e2) 提交树 keys = …`，见
[gate-recheck-5c-run.txt](gate-recheck-5c-run.txt)（那份的 `工作树与提交树一致` 是**真的**，
因为提交树刚追上工作树 —— 不是尺子失效）。
