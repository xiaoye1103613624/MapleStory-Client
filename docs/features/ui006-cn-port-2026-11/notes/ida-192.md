# IDA 192 客户端逆向调研：魔女森林(CN_50100) / 突破石(CN_Limitbreakthrough)

- 任务：只读逆向调研，为 UI006 CN 移植寻找 192 客户端二进制中的**原生逻辑证据**。
- 执行 agent：`ida-192-recon`（子任务）；时间：2026-11-21（Asia/Shanghai）。
- 结论摘要：**192 客户端二进制中未发现这两个 UI 的任何原生代码/字符串/协议入口**。客户端被加壳/混淆且 IDB 几乎无分析结果，二进制内物理上不存在目标字符串。资源侧（WZ/IMG）两个 UI 节点确实存在。因此“只移植资源 + 自建 UI、无协议”是本方向上**唯一可行的路径**，但协议/数据字段语义**无法从该二进制取证**，必须由服务端行为或运行期抓包另行确认。

## 2. 决定性事实：`idb_open` 后的分析深度近乎为零

`server_health` 确认 `input_path` 正确，`auto_analysis_ready=true`、`hexrays_ready=true`，但：

```
survey_binary.statistics = {
  "total_functions": 3, "named_functions": 1, "unnamed_functions": 2,
  "total_strings": 10, "total_segments": 8
}
strings_cache_size = 10
imports = 仅 1 条：kernel32!lstrcpy @0x14749b047
names 总数 = 21（几乎全是 TLS/导入桩）
```

- `list_funcs` / `func_query(name_regex=".*")` 只返回 3 个函数：
  - `start` @ `0x149c88000`（size 9）
  - `sub_149C88009` @ `0x149c88009`（size 0x43）
  - `sub_149C8804C` @ `0x149c8804c`（size 0x30）
- 即便把 `run_auto_analysis` 从 `false` 改为 `true` 重开，`is_analyzing` 立刻为 `false`、函数数仍是 3 —— IDB 本身没有被逆向出海量的游戏代码。

**段布局异常（加壳典型特征）**：`___` 段 VS=0x741e000 但 raw size 仅 0x20f0200（约 90% 零填充）；末段名 `zytsjlrd`、`llbfkknc` 为随机化命名；首段 4MB 采样熵 **7.900**（接近 8，表明加密/压缩数据）。

**仅有的 3 个函数反编译结果（伪代码摘要）**：

```c
// 0x149c88000 start
void __noreturn start(){ sub_149C88009(); __debugbreak(); }

// 0x149c88009
__int64 __fastcall sub_149C88009(__int64 a1, __int64 a2, __int64 a3, __int64 a4){
  v4 = v6 - 15548424;
  if ( *v6 == 0xCC ) { *v6 = 0; v4 = sub_149C8804C(a1,a2,a3,a4); }  // self-modifying: 0xCC 断点触发解压
  return v7;
}

// 0x149c8804c —— 解密/解压存根
__int64 __fastcall sub_149C8804C(/*8 args*/){
  for (i = v13 >> 2; i != 0; --i) { *v8 ^= v14; *v8++ += v15; }  // 32-bit XOR + ADD 滚动解密
  return v11;
}
```

这说明 192 客户端的真实逻辑在运行时由该存根解密还原，静态 IDB 中**没有可反编译的游戏主体代码**。

## 6. 局限说明（如实）

1. **加壳/混淆**：首段熵 7.90、90% 零填充 raw、`zytsjlrd`/`llbfkknc` 随机段名、自修改解密存根 —— 真实代码在运行时还原，静态 IDB 无法覆盖。
2. **IDB 分析深度不足**：仅 3 函数 / 10 字符串 / 21 名称 / 1 个导入；即使重开启用 auto-analysis 也无改善。`nam` 文件仅 16KB 且被占用。
3. **反作弊/在线环境**：`BlackCipher`、`Xigncode`、`MapleSecurePC64.dll`，配置指向在线服务器，不适合动态附加/抓包取证（本次亦未做动态调试）。
4. **无可用 xref/decompile 目标**：因 0 命中，步骤 4 的「xrefs_to → decompile → 提取 opcode/UI 类/Send 包/路径拼接/按钮分支/Timer/Number/Grade 来源」全部无法执行；报告中不虚构任何 opcode 或包结构。

## 7. 对移植的结论（回答 lead 的三个问题）

1. **192 客户端是否有这两个功能的原生逻辑入口？**
   **否（就本 IDB 静态取证而言）**。二进制中不存在相关字符串、函数或协议符号；唯一代码入口是加壳解密存根。不能据此断言运行期完全没有逻辑（加壳后运行时可能存在），但**没有可被静态利用的原生实现**。

2. **资源路径是什么？**
   `UI/UIWindowCN.img/CN_50100` 与 `UI/UIWindowCN.img/CN_Limitbreakthrough`（在 `Data/UI/UI_006.wz` 内）。这是本次由仓库既有的 orange-wz 全树证据确认的路径；IDA 侧无法提供路径拼接代码证据。

3. **可否只移植资源 + 自建 UI 而无协议？**
   **可行且为唯一现实路径**：既然 192 静态侧拿不到协议，移植只能把 `CN_50100`/`CN_Limitbreakthrough` 资源（经 orange-wz 按 AGENTS.md 的跨客户端密钥转换硬门禁导入，注意 192 零 IV → 目标 GMS IV 转换与本端 probe/短启验收）接入自建 UI，按钮/动画按资源节点名还原。但必须明确：**交互后的数据变化（突破结果、次数、Timer、Grade、奖励）无协议来源，需要服务端模拟或本地构造数据**；本调研无法提供 Send 包结构或 opcode。若要求“与原生一致的逻辑/协议”，则本客户端不足以支撑，需另找未加壳的客户端版本或运行期抓包。
