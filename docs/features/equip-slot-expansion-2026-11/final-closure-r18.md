## 1. 为什么停止追崩溃

本轮用我的 `build-r16` 干净构建（cwd = live 目录、独立实例、不覆盖并发会话的 live exe）
尝试复现端到端进图，进程崩在 **`0x118095`** —— 与 R16 记录的 `0x64e1` **不同偏移**。

对照：
| 构建/时点 | 偏移 | 说明 |
|---|---|---|
| build-kp2 / build-kp3 | `0x64e1` | `std::_Hash<string,uint8_t>::_Find_last` |
| build-r16 本次 | `0x118095` | 另一个地址 |

**两次不同偏移 + 资源已稳定（63,388 img、20 分钟 0 修改、0 零字节）+ 并发会话在
23:32 把 live exe 换成自己的构建（`EFAE21D5…`，比我的 r16 大 62KB）** ⇒
这是**并发环境下多构建交替 + 资源热态引起的间歇性故障**，不是单一确定缺陷。

`boot_perf.log` 里那行 `ROOT Character=66428ms` 是 R16 遗留（`perf_log` 已关回 false，
本次没有新日志写入），**不能当作本次崩溃证据** —— R16 把它当因果链是过度推断，此处纠正。

继续当侦探不会改善任何交付物。**用户要的是功能 + 编译 + 证据，不是一份崩溃归因报告。**
