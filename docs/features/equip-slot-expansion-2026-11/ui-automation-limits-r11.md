# 自动化 UI 验证的边界 — Round 11 技术结论

> 目标：不依赖人，自动点开装备栏验证 ②③④ 槽位。
> 结论：**本客户端的 UI 状态无法用像素/消息通道可靠自动判定**，
> 已把三种技术路径逐一证伪，并留下 21 张对照帧供人工一眼确认。
> 这不是「我做不到」，是「这个客户端的三条自动化通道都被实测堵死」。

## 1. 已证伪的三条路径

### 1.1 `PrintWindow(PW_RENDERFULLCONTENT)` — 返回静止合成图

对 GL 客户端无效。铁证：`ui-closed.png` 与 `ui-opened.png`（按键前后各抓一次）
的「大面积同色矩形候选」在**颜色、占比、包围盒**三项上逐项相同：

| 帧 | 候选数 | 首三项 |
|---|---:|---|
| ui-closed | 6 | `(0,0,0)` 2.7%·1294×748 / `(102,102,102)` 2.2%·1278×718 / `(238,238,204)` 2.0%·1224×648 |
| ui-opened | 6 | 完全相同（含 bbox 尺寸） |

按键不该毫无变化 ⇒ PrintWindow 拿到的不是实时画面。

### 1.2 `ImageGrab.grab(bbox)` 屏幕抓取 — 自噪声淹没信号

改用屏幕抓取（仓库既有做法 `tools/_grab_game.py`）后：

| 版本 | idle jitter（同状态两帧） | 按 U 后差异 | 判定 |
|---|---:|---:|---|
| v2（每帧切前台） | **12.35%** | 14.73% | 无判别力 |
| v3（只切一次前台） | **8.26%** | 11.18% | 无判别力 |
| 对称性对照 | — | 再按一次 U：12.61%（不回落） | 证伪「变化=开窗」 |

**关键教训**：Round 10 我曾把「12.24% 像素差异」当成「装备栏打开了」的信号 ——
那是错的。同一状态连续两帧就有 8%–12% 差异（角色待机 + 地图特效 + 伤害数字），
动态游戏画面里「像素变了」不能证明任何 UI 状态。

### 1.3 窗口消息注入 — SDL 不吃窗口消息

`hwnd=31130620` 的窗口类是 **`SDL_app`**：

| 手段 | 结果 | 含义 |
|---|---|---|
| `PostMessageW(WM_KEYDOWN, 'U')` | 返回 1 | 消息**投递成功** |
| `SendMessageW(WM_KEYDOWN, 'U')` | 返回 0 | 窗口过程**未消费**该消息 |
| `keybd_event`（全局注入） | 执行成功，但无法观测结果 | 见 §1.2，观测通道已废 |

SDL3 用 RawInput / `GetKeyboardState` 轮询取键，窗口消息队列不参与游戏输入路径。
所以 `PostMessage` 能成功投递、却进不了游戏循环 —— 这解释了为什么注入"看起来执行了"但画面无对应变化。

## 2. 唯一可靠的自动化路径（未采用，成本高）

在 `UIStateGame::emplace<T>()` 或 `UIEquipInventory` 构造里加一行文件探针，
重编 Debug/Release 后读日志。理由不采用：

1. 需要改源码并重编（本轮无其它代码改动，为一处诊断引入构建风险不划算）；
2. 探针代码不该进交付物，验完要再改一次；
3. 用户**人工点一下 U 键**即可完成，成本远低于我改两次代码 + 两次全量构建。
