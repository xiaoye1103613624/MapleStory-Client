## 0. 关键结论（先看这 6 条）

1. 参考客户端的 33 项扩展功能**不在 `BeiDou.exe` 里**，全部在 `ijl15.dll` 插件（IDA 侧表现为 hook + 自建 UI 层），配套资源在 `Data/UI`。所以“对齐 exe 版本”没有意义，要对齐的是**插件行为 + UI 资源**。
2. 实施依据为 **D3 的纯逆向**：`ijl15.dll` 保留完整 MSVC 修饰名，37 项中 35 项已定位到函数与 EA（见 `r01-module-map.md`）。`E:\MXD\自定义功能实现\` 仅用于确认需求语义与命名，**不作为地址/协议依据**。
   - **补充实证（2026-10-21）**：`怪物图鉴`、`长伤害显示` 在 V17.7 的 `ijl15.dll` 中**零符号、零字符串**（ASCII + GBK 双扫），`BeiDou.exe` 与其它 dll 同样无命中；二者实际来自另一套开发构建 `F:\MXD_dev\BeiDou-ijl15`，且长伤害模块自身处于「已实现未接线」休眠态。按 D7 仍新增，但性质是**新功能**而非对齐。
3. 当前客户端已有扩展 opcode 通道（`PacketSwitch` 的 0x37xx 动态注册），原生移植不需要 hook，**风险显著低于插件方案**，这是本次移植最大的有利条件。
4. **存在 opcode 冲突**：参考端 `0x3730 = CASHSHOP_WINDOW_ACTION`，当前端 `0x3730 = LIMIT_BREAK_SYNC`。窗口现金商城移植时必须重新分配。
5. **当前客户端缺少基础仓库（Trunk）功能**：`STORAGE(309)` 只在调试名表里出现，没有任何 handler。因此“更高仓库列表”不能单点移植，必须先补基础仓库——这是参考清单之外的基础缺口。
6. 当前工作区有 **463 项未提交改动**（147 tracked + 316 untracked），功能移植必须建立在干净基线上，否则后续无法定位回归。

## 3. opcode 规划（移植前必须先定）

当前端已占用：`0x3730 = LIMIT_BREAK_SYNC`（`Net/Handlers/CommonHandlers.h` + `PacketSwitch.cpp:137,606`）。

| 参考 opcode | 参考用途 | 处置建议 |
|---|---|---|
| 0x1000 | HP/MP 警报 | 可沿用（v83 空闲段），落地前校验 |
| 0x3713 | 团队 Buff / 通用自定义包 | 可沿用 |
| 0x3714 | 伤害统计 | 可沿用 |
| 0x3724 / 0x3725 | 收纳背包 请求 / 快照 | 可沿用 |
| 0x3726 / 0x3727 | 他人装备详情 请求 / 回应 | 可沿用 |
| 0x372B / 0x372C | 怪物图鉴 请求 / 回应 | 可沿用 |
| **0x3730** | 窗口现金商城 动作 | **冲突，改 0x3740** |
| 0x3731 | 窗口现金商城 同步 | 可沿用（建议同步改 0x3741 保持成对） |
| 0x373D / 0x373F | 天气系统 | 可沿用 |
| 0x8000 / 0xFF00 | 长伤害 / 属性详情（插件内部） | 当前端不需要，忽略 |

**规则**：新功能统一在 `0x3740–0x37FF` 段按 2 个 opcode 一组（req/resp）分配，写入 `Net/PacketSwitch.cpp` 的枚举与 `opcode_msg` 表，并在功能文档登记。

## 5. 实施规范（每批都要遵守）

1. **不回退**：任何批次不得改变现有已验收功能的坐标/交互；改动前先截图留证。
2. **闭环**：功能 = 逻辑 + 资源 + 配置 + 文档（`docs/features/<name>/README.md` + `manifest.md` + `evidence/`）。
3. **有注释 + 分级日志**：调试期开 `LOG_DEBUG`，功能完成后清理临时日志。
4. **单功能单提交**：按仓库 `git-commit-standard` 规范，原子提交。
5. **验收**：每批必须跑“登录→选角→进图→背包→商店→技能→任务”主链，外加该功能专项路径。
6. **UI 作图**：若需重绘，走 Photoshop MCP + 原生 UI 样板库，PSD 分层保留。
