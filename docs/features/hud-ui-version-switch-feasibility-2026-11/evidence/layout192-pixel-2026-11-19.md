## 2. 快捷键“键帽 / 2 行 × N 列”布局依据（本次核心发现）

### 2.1 IMG 侧：quickSlot 子树**没有**独立键帽 / 数字标签节点

`mainBar/quickSlot` 子树共 28 个 canvas（`wz_qs_keycap.out`，`parse_qs_keycap.py` 输出），完整清单：
`backgrnd / layer:cover / button:Extend(4态) / button:Fold(4态) / button:Extend800(4态) / button:Fold800(4态) / setting/backgrnd / setting/button:Complete(4态) / setting/button:Cancel(4态) / selected/0`。
- **不存在** `key*` / `num*` / `label*` / `hotkey*` 之类键帽 canvas；`search_node kw=key/Key/num/slot` 在 `mainBar/quickSlot` 下命中 0 个键帽节点。
- **结论（可信度：高）**：用户真机看到的“右下大片空灰格、无键帽”——灰格来自 `backgrnd`(557×67) + `layer:cover`(562×73) 两张底板；键帽/图标**不是 StatusBar3.img 提供的**，而由客户端逻辑（技能/快捷键图标层）绘制。因此“按 192 素材还原键帽”在 IMG 侧**无节点可依**，须走逻辑层（见 §2.2）或用户确认是否自绘。

### 2.2 IDA 侧：`s_ptShortKeyPos` 内存表 = 2 行 × 14 列 = 28 槽（**不是 2×10**）

- 函数：`CQuickSlot::GetPosByIndex@0x16968F0`（`_raw_quickslot_getposbyindex.c`）：
  ```
  if ( nIdx < this->m_nQuickSlotDisplayNo ) {
    *x = s_ptShortKeyPos[nIdx].x;  /*0x1696907*/
    *y = s_ptShortKeyPos[nIdx].y;  /*0x1696914*/
  }
  ```
- 符号：`s_ptShortKeyPos @ 0x279C390`（`list_globals` 实测，非推测）；哨兵表 `s_ptShortKeyPos_0 @ 0x27C5978` 全 0。
- 本次 `get_bytes(0x279C390, 256)` 实读（小端 i32，每槽 8B），**28 个有效槽**：

| 行 | y | x 序列（pitch=33） | 槽 idx |
| --- | --- | --- | --- |
| 上排 | 15 | 7, 40, 73, 106, 150, 183, 216, 249, 282, 315, 348, 381, 414, 447 | 0-3, 8-11, 16-19, 24-25 |
| 下排 | 48 | 7, 40, 73, 106, 150, 183, 216, 249, 282, 315, 348, 381, 414, 447 | 4-7, 12-15, 20-23, 26-27 |

（idx28+ 落入相邻全局变量 `0x02575758` 等，非槽位，`get_bytes` 越界读数，不作坐标。）

- **结论（可信度：高）**：原生快捷栏是 **2 行 × 14 列 = 28 槽**，列距 33px、行距 33px，上排 y=15、下排 y=48（相对快捷控件 TL）。**用户描述的“2 行 × 10 列”与反编译证据不符**（可能是某分辨率裁剪后的可见列数，或对另一版本客户端的印象）。若目标是“功能完整还原”，应按 28 槽表实现；若确需 2×10，属**超出原生的改造**，须用户拍板。
- 对照既有证据：`ida-statusbar2-layout-2026-11-19.md §2.4` 早先只读到 idx0-11 便推断“28 槽需要完整宽度”，本次补全为 28 槽全表并钉死 2×14，口径更新。
- `s_ptShortKeyPos` 是 **StatusBar2 逻辑常量表**（MapleStoryT.exe），StatusBar3 IMG 只有 557×67 底板；28 槽 × 33px pitch 最大 x=447+32=479 < 557 宽，槽位落在底板内——两者几何相容，但**不能据 IDA 表宣称 StatusBar3 也按此绘制**（无 StatusBar3 逻辑证据，标局限）。

## 5. 未确证 / 局限汇总（禁猜测）

1. **无 192 StatusBar3 的 C++ 反编译**：本 IDA（MapleStoryT.exe）二进制内只有 StatusBar2 路径，StatusBar3 的像素布局逻辑（菜单排布、页签创建、快捷键图标层）**不存在于本 IDB**，不能据 IDA 宣称 192 StatusBar3 的精确 x/y。
2. **键帽/图标层**：IMG quickSlot 子树无键帽节点；键帽由运行时技能/快捷键图标层绘制（IDA 仅给出 28 槽坐标表，且属 StatusBar2 逻辑）。“192 素材按 192 反编译文件做像素级代码还原”在键帽一项上**缺 192 二进制 + 缺 IMG 节点**，须补资源或用户确认自绘方案。
3. **2×10 vs 2×14**：用户描述与反编译表冲突；本报告采信 IDA 内存表（2×14=28），标注“若坚持 2×10 属改造”。
4. **页签语义**：6 页签英文节点名无法证明中文“全体/战斗/组队/好友/公会/联合”的一一映射；`union` 是 submenu 按钮非聊天页签。中文标签以真机/用户确认为准。
5. **origin None**：多数 `get_node_detail` 返回 `origin=None`（WZ 未显式写），运行时默认 (0,0)；快捷栏两节点有显式 origin 已取到。像素落点仍需真机抓帧复核。
6. **未做真机渲染验证**：本报告为纯静态只读取证（orange-wz + IDA + 源码），所有“修复后观感”结论标“待真机验收”。
7. **StatusBar2 与 StatusBar3 混用风险**：IDA 数值（881,2 / 67 / 2×14 表 / 7 页签 flag）来自 StatusBar2 契约；用于 StatusBar3 前须逐项证明兼容，本报告只作“逻辑参考”，不作“StatusBar3 像素依据”。
