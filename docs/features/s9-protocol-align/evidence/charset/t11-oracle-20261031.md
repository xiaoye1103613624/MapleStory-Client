## 3. 断言与结果

`charset_check.cpp` 对每条向量断言三件事，另有 4 条边界断言。合计 **73 条断言，failures=0**（程序退出码即失败条数）。

| 断言 | 含义 | 结果 |
| --- | --- | --- |
| `to_internal` | 线上 GBK 字节 → 内部 UTF-8，与 Python 算出的 UTF-8 逐字节相等 | 23/23 PASS |
| `from_internal` | 内部 UTF-8 → 线上 GBK，与 Python 算出的 GBK 逐字节相等 | 23/23 PASS |
| `roundtrip` | `from_internal(to_internal(gbk)) == gbk` | 23/23 PASS |
| `invalid utf8 passthrough` | `"abc\xFFtest"` 原样发出（8 字节不变） | PASS |
| `truncated utf8 passthrough` | `"hi\xE5\x28"`（截断的多字节序列）原样发出 | PASS |
| `ascii identity`（两个方向） | 纯 ASCII 字节级不变 | PASS |

`roundtrip` 这条是**给"服务端给的串再发回去"的路径兜底**用的：公会名 / 角色名 / 密语目标名都是
`read_string()` 拿到后存进模型、再由某个 `write_string()` 发出去（如 `Net/Packets/GuildPackets.h:33`、
`Net/Packets/MessagingPackets.h:80`）。只要往返不闭合，这类字段就会在二次转换中漂掉。

## 5. 非法 GBK 入站：只观测，不判定

Windows 的 `MultiByteToWideChar(CP936, 0, ...)` 用 **best-fit**，行为不在 GBK 规范里，所以我没有对它下断言，
只把实际结果记下来（证明"不崩、不整段丢"）：

| 输入（hex） | 输出（hex） | 解读 |
| --- | --- | --- |
| `41 D2 42` | `41 E8 A4 BA` | `0xD2 0x42` 本身是**合法** GBK 双字节字，于是 `B` 被当成尾字节吃掉 ⇒ 不是 bug，是 GBK 的固有歧义；上游若真发这串，语义本来就该是双字节 |
| `41 D2`（落单的引导字节） | `41 3F` | 残缺对替换成 `?`，`A` 保住，不崩 |

出站方向反过来是**严格**的：`MultiByteToWideChar(CP_UTF8, MB_ERR_INVALID_CHARS, ...)` 一失败就整体原样发出，
把"转换失败"降级成"维持转换前的行为"，绝不把字段写空。这条是 175 个 `read_string` / 74 个 `write_string`
调用点里可能存在的"直接塞裸字节"用法的安全网（§5.2 的双重转换顾虑也由此覆盖：ASCII 恒等，非 ASCII 才转）。
