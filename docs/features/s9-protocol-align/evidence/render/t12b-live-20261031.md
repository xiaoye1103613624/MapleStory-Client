## 结论

**修复生效，且是可用像素读出来的。** classic 聊天栏的聊天目标芯片（`对所有人`）用
`Text::width()` 做手动居中，同一个 81px 贴图、同一串 4 个汉字：

| 构建 | 蓝底 x 范围 | 字形 x 范围 | 字形实宽 | 左内缩 | 字形中心 − 蓝底中心 |
|---|---|---|---|---|---|
| old（T11 构建 `e1394e51`，修复前） | 11..84（w=74） | 14..54 | **41 px** | **3 px** | **−13.5 px** |
| new（T12b 构建 `6da3c2f6`，修复后） | 19..92（w=74） | 35..76 | **42 px** | **16 px** | **+0.0 px** |

两行读法：

1. **字形实宽 41 → 42 px 没变** ⇒ 绘制侧（`drawtext`）的推进量从头到尾就是真字形宽，
   这次改的确实只有度量侧，没有顺手改动画出来的东西。
2. **左内缩 3 → 16 px、居中偏差 −13.5 → 0.0 px** ⇒ 度量值从"按字节数空格宽"变成
   "按码点数真字宽"，居中算式随之落回正中。

上表的 x 是**各自帧内的图像坐标**，两帧路由不同、差一个 (8, 30) 偏移；但本次判据取的三个量
（字形实宽、左内缩、字形中心−蓝底中心）都是**同一帧内两个边缘之差**，与抓帧偏移无关。
偏移方向由蓝底自身校准：old 蓝底 x 11..84，new 蓝底 x 19..92 ⇒ 减掉 8 后两侧完全重合，
即芯片在客户区里根本没动过（宽都读成 74 px）⇒ 差异只可能来自文字摆放，不是布局或抓帧。

## 为什么选这一处做 A/B

全仓唯一一处"把 `Text::width()` 直接写进几何、且屏幕上恒定有中文"的点：

[IO/UITypes/UIChatBar.cpp:301-305](../../../../../IO/UITypes/UIChatBar.cpp)

```cpp
int16_t target_w = classic_target_text.width();
// 下限 2：私聊对象名可能长过 81px 的贴图，居中会把文字推出框左沿。
int16_t target_x = target_w > 0 ? std::max<int16_t>(2, (CHAT_TARGET_W - target_w) / 2) : 9;
classic_target_text.draw(input_pos + Point<int16_t>(target_x, -4));
```

`CHAT_TARGET_W = 81`（[IO/UITypes/UIChatBar.h:185](../../../../../IO/UITypes/UIChatBar.h)），
文本是 `Text(A11M, LEFT, WHITE, "对所有人")`（`UIChatBar.cpp:134-136`，硬编码 UTF-8 字面量，
不经封包 ⇒ 与 T11 无关，两帧可比）。

### 算式预测 vs 实测

A11M 的空格推进量 = 6 px，11px 字号的汉字推进量 = 11 px（均由
`tools/probe/utf8_metrics_check.cpp` 现算，见下）。

| | `width()` 度量 | `target_x = (81 − w)/2` | 实测左内缩 |
|---|---|---|---|
| 修复前（按字节） | 12 字节 × 6 = **72** | **4** | 3 |
| 修复后（按码点） | 4 码点 × 11 = **44** | **18** | 16 |

预测位移 = 18 − 4 = **14 px**；实测位移 = 16 − 3 = **13 px**。
两帧实测都比预测小 1–2 px，方向一致、量级一致 —— 来自蓝底左沿把贴图 1px 亮边算进去、
以及首字形的左侧空隙，不是算式不符。

## 离线门禁（先于真机跑通）

`tools/probe/utf8_metrics_check.cpp`（独立编译，不进 vcxproj/CMake）：

```
decode:   vectors=26 bytes=252 failures=0
freetype: compared=3570 missing=60 mismatched=0 ascii_ax=[6,8] cjk_ax=[11,15]
RESULT failures=0
```

- **`mismatched=0` 是这次修复的地基**：度量侧新写的 `wide_advance()` 走
  `FT_Load_Glyph(FT_LOAD_DEFAULT)` + `advance.x >> 6`，绘制侧走 `FT_LOAD_RENDER`。
  图集 `locked` 时度量仍要能算，所以不能直接问图集；这条"两种 load flags 的 advance 相等"
  是承重假设，3570 次比对 0 反例才敢用（[Graphics/GraphicsGL.cpp:1236](../../../../../Graphics/GraphicsGL.cpp)）。
- `missing=60`：60 个码点（谚文/emoji）在 SimHei 里取不到字形 ⇒ 度量返回 0，
  与"画不出东西"一致，不再按 3 个空格宽虚增。
- 向量表由 `tools/probe/gen_utf8_vectors.py` 用 Python `utf-8` codec 现算期望值生成，
  含 6 条 `lax:` 向量钉住解码器的**宽松**行为（不校验尾字节、不拒过长编码、≥0xF8 引导字节照收）——
  这是修复前后一贯的既有行为，写进 [Graphics/Utf8.h](../../../../../Graphics/Utf8.h) 的注释里，不当"已修"也不静默改。

## 改动本体：一份解码，两处调用

根因是 UTF-8 解码被**手写了两遍**：度量侧按字节、绘制侧按码点 ⇒ 量出来的宽度和画出来的
推进量天然对不上。修法不是给某处补系数，而是把解码收成一个函数，让不变式变成结构性的：

- 新增 [Graphics/Utf8.h](../../../../../Graphics/Utf8.h)：`ms::utf8_next(text, pos, last, consumed)`。
- 度量侧：`LayoutBuilder::measure()` / `wide_advance()`
  （[Graphics/GraphicsGL.cpp:1224](../../../../../Graphics/GraphicsGL.cpp)、`:1236`），
  `wordwidth` 循环改按码点推进（`:1154`），`advances` 循环同一码点的各字节共享该码点起笔
  （`:1199-1210`，保持**按字节下标**，`Textfield` 的光标仍用 `advance(byte)`）。
- 绘制侧：`drawtext` 内层循环改调同一个 `utf8_next`
  （[Graphics/GraphicsGL.cpp:1354-1359](../../../../../Graphics/GraphicsGL.cpp)）。

## 英文布局回归

- ASCII 分支 `cp < 128 → font.chars[cp].ax` 与改动前的 `font.chars[uc].ax` 是同一张表的同一个
  表达式，且解码器对 `< 0x80` 恒等返回（向量表覆盖）⇒ 英文度量逐字节不变。
- 真机同屏旁证（new 帧）：`Ver. 0.0.1`、`[Welcome] Welcome to Scania!`、
  `[Welcome] Welcome to MapleStory!!`、角色名标签 `Admin` 排布与 old 帧一致，无位移、无粘连。
- 换行判据由 `last-first==1` 推广为 `i == first`（单码点即超宽）⇒ 英文单词行为等价。
